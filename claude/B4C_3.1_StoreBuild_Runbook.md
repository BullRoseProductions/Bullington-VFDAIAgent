# B4C — 3.1 store build (get releases 13–18 onto phones) — BUILD ORDER for CC

**Decision (Ashlea, Oct 20):** We are **NOT adopting Capgo.** It was wired into the code Sept 24 (`89f3ffe`) but never set up — Ashlea confirmed on capgo.app there's no login and no Capgo API key, so **no account was ever created and no bundle was ever uploaded.** (The stray `.capgo-credentials` folder on the Mac is just empty scaffolding the install left behind, not a real account — nothing to close out.) New builds reach phones through the **app stores**, same as always. This release does two things: (1) rip out the dead Capgo wiring so it stops implying a service that doesn't exist, and (2) cut a normal 3.1 store build that carries releases 13–18.

**Presence stays Path A** (geofence-only). No native/presence change, no new permission, no privacy-label change. Fork doc: [[B4C_iOS_Presence_Privacy_vs_Reliability_Fork]].

**What's shipping to phones:** releases 13–18 (probation, qualifications, scroll restore, expirations, readiness scorecard, onboarding item-config) — all JS/web, already web-live on `main` (`207f888`). The DB security fixes (apparatus, apparatus_maintenance, members cross-dept, admin-gate `f040899`) are **already live on both web and native** — they're DB policies, they went live the moment they were applied, no build needed. So this build is purely about carrying the **UI layer** onto installed apps.

**Two separable steps, two separate reviews.** Step 1 (Capgo removal) is a code change — I gate-review the diff before it's built. Step 2 (version bump + build) is routine. Keep them as two commits so if anything in the removal review needs a second look, the version-bump build isn't held hostage to it.

## STEP 1 — Remove the dead Capgo wiring (deliver as a diff for my review BEFORE building)

The goal is a **behavior-neutral** removal: on phones today Capgo does nothing, so after this, phones behave identically — minus a dormant plugin that was pretending to be a service. The trick that keeps the diff tiny: `src/liveUpdate.js` keeps its five exported function names, they just become inert no-ops, so **`src/main.jsx` and `src/appUpdate.js` need no change.**

### 1a. `src/liveUpdate.js` — drop the `@capgo` import, stub the functions
- Remove the dynamic `import("@capgo/capacitor-updater")` block (the `~lines 57–61` loader that sets `const { CapacitorUpdater } = mod`).
- The five exports stay, as inert stubs that preserve their signatures and return types:
  - `markBundleHealthy()` — was `await p.notifyAppReady()` (~line 82) → now a no-op `async` that returns immediately.
  - `currentBundle()` (~line 96) → returns `null` (or the same shape it returned on web today).
  - `setChannel(channel)` (~lines 108–112) → no-op `async`.
  - `revertToStoreBundle()` (~line 120) → no-op `async`.
  - `watchLiveUpdates()` (~line 133) → no-op `async`.
- No remaining reference to `CapacitorUpdater`, `@capgo`, `notifyAppReady`, or `setChannel({channel})` anywhere in the file.
- Leave the file's header comment, but reword the "Capgo owns native web-layer updates" lines so they don't claim a live service. (Same for the stale comments in `src/main.jsx` ~lines 45/77 and `src/appUpdate.js` ~line 33 — reword, don't claim Capgo is doing anything.)

> Why stub instead of delete the file: `src/main.jsx` imports `{ markBundleHealthy, watchLiveUpdates }` at line 8 and calls them. Keeping the exports as no-ops means `main.jsx` is untouched and the diff is confined to the files that actually mention Capgo. Deleting the file would force a `main.jsx` edit and widen the review surface for zero benefit.

### 1b. `package.json`
- Remove the dependency line (~line 24): `"@capgo/capacitor-updater": "^8.51.23"`.
- Run a fresh `npm install` so `package-lock.json` drops the dependency too. Include the lockfile change in the diff.

### 1c. Native plugin registration (all of these go together — a half-removal breaks the build)
- `capacitor.config.json` — remove the `CapacitorUpdater` config block.
- `ios/App/App/capacitor.config.json` — same block (synced copy).
- `android/app/src/main/assets/capacitor.config.json` — same block (synced copy).
- `android/app/src/main/assets/capacitor.plugins.json` — remove the Capgo entry (~lines 19–20).
- `android/capacitor.settings.gradle` — remove the `include ':capgo-capacitor-updater'` + project-dir lines (~lines 17–18).
- iOS Podfile / Podfile.lock — **nothing to do** (confirmed: no Capgo pod is present).

### 1d. Re-sync and sanity-check
- `npm run cap:sync` (= `build:native` + `cap sync`) — this regenerates the native plugin lists from the now-clean config. After it runs, re-grep the three `capacitor.config.json` copies, `capacitor.plugins.json`, and `capacitor.settings.gradle` to confirm **zero** `capgo` / `CapacitorUpdater` references survive the sync.
- `npm run build:native` must pass eslint and build clean (no unresolved `@capgo` import).

**Deliver to me as a diff (`git diff` on the Step-1 commit) + the post-sync grep output.** I review that nothing outside the listed files changed, the five exports still exist with their signatures, `main.jsx` is untouched, and no `capgo`/`CapacitorUpdater`/`verified` token slipped in or out. Then Step 2.

## STEP 2 — Version bump + store build (routine, Path A unchanged)

### 2a. Bump versions (keep iOS/Android in step)
- **iOS** — `ios/App/App.xcodeproj/project.pbxproj`: `MARKETING_VERSION` `3.0` → **`3.1`**; `CURRENT_PROJECT_VERSION` `13` → **`14`** (every occurrence — there are usually two, Debug + Release).
- **Android** — `android/app/build.gradle` (~lines 19–20): `versionName "3.0"` → **`"3.1"`**; `versionCode 11` → **`12`**.

### 2b. Build from production src
- Build the native app from the src carrying 13–18. Before building, confirm `git log` shows the Step-1 removal commit on top of the release-18 web code (`207f888` lineage) — i.e. the bundle carries probation/qualifications/expirations/readiness/onboarding. Quick proof: grep the built `dist/assets/*.js` for a readiness + onboarding string (e.g. "Mark ready for sign-off", the onboarding sign-off queue label) so we know the store build actually contains the new UI, not a stale bundle.
- `npm run cap:sync` once more if 2a edited anything cap reads (it doesn't touch the version files, but sync is cheap and keeps native current). **No change to `src/geofence.js`, Info.plist permissions, AndroidManifest, or the privacy label** — Path A.

### 2c. Submit
- **iOS:** `npm run cap:ios` → Xcode → Archive → upload to App Store Connect → submit for review.
- **Android:** `npm run cap:android` → Android Studio → signed AAB → Play Console → submit.
- Because nothing about location/permissions/plugins-the-store-cares-about changed (we only *removed* an updater and bumped a version), expect a routine review — no new privacy disclosures.

## Reviewer gates (same discipline as every release)
- **Before Step-1 build:** I review the removal diff + post-sync grep (behavior-neutral, confined to the listed files, exports preserved, `main.jsx` untouched).
- **Before Step-2 submit:** version bump is the only functional diff beyond the removal; `geofence.js` byte-identical Path A; privacy label unchanged; built bundle proven to carry 13–18.
- **Built ≠ live.** Nothing is "on phones" until the store build is **Approved** and each member updates. Store review takes days; adoption is partial and trickles in as people update. The truth doc (`B4C_Whats_Actually_Live.md`) flips the native column from "web-only" to "on phones (3.1)" **only after** the build is Approved and we've seen it on a real device — not at submit.

## Honest-state notes
- This does not make future updates faster — every future UI change still goes through a store build until/unless we ever adopt a real OTA service. That's the tradeoff Ashlea accepted by not setting up Capgo, and it's the right call for where B4C is.
- There is no rollback-to-prior-bundle button anymore (that was Capgo's only real feature, and it was never functioning). Rollback for a bad store build is: submit a fixed build. Same as it's always actually been.
